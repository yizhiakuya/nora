# 服务重启后的安全续跑

## 现有链路与缺口

`ChatTurnRunner` 先创建 `chat_run`、写用户消息，在每个工具首次出现和终态写 `agent_step`，整轮结束才保存助手消息。`StaleRunRecovery` 启动时只修改运行状态。进程突然退出后，工具结果仍在步骤表，但聊天和下一次模型请求都看不到这些结果；补充要求的聊天分段也没有恢复。等待审批与实际执行共用 running，无法区分未执行和结果未知。

## 最小方案

- 沿用现有运行、步骤和消息表，不增加执行引擎、重放缓存或新的续跑接口。重启自动恢复记录；用户点击“继续任务”走原有发送链路，追加继续要求，保留历史和输入框草稿。
- 消息关联 `run_id`；原始用户消息和助手消息保存已有 `TaskContext`，续跑沿用资料引用和检索范围。加载历史同时返回运行状态，队列不会在中断后自行推进。
- 同一次运行的终态只标记最后一个助手分段，避免把插入要求之前已结束的段落也显示为刚刚中断。
- 创建运行与初始用户消息在同一事务写入。工具状态明确区分 pending（尚未执行、含等待审批）和 running（即将实际调用）；状态变化及终态写入步骤日志后才对外发布。工具日志写入失败必须停止执行链路。
- 步骤日志补存现有 context 字段，保存真实的补充要求边界。启动恢复按原步骤顺序折叠同 ID 的状态：终态保留，pending 标为未执行，running 标为结果未知，保留参数供核实；中断的文本只保留已落库部分，不虚构完成结果。
- 在同一事务中恢复助手消息并标记运行终态，复用 `saveAssistantTurn` 的聊天分段。已保存助手消息的运行不重复生成记录；用户已要求取消的轮次恢复为 cancelled。重复启动不会新增副本，已删除的会话不恢复。
- 恢复在 Spring 单例初始化完成后、Web 服务开始接受请求前执行。复用审批服务的 `clearPending` 清理恢复会话的 Redis 票据；原执行线程已消失，旧审批不能继续使用，续跑需要重新审批。
- 继续任务保留已完成结果。未知结果是核实线索，不是可重试失败；提示词要求先核实实际状态，无法核实则向用户确认，不原样重放。

## 验收

使用真实模型、真实文件工具和真实进程退出验证：完成写入后、写入发生但终态尚未保存时、等待审批时分别重启。检查文件操作仅执行一次、工具状态诚实、补充要求的聊天顺序与资料范围保留、重复重启无重复消息，以及用户取消不自行续跑。浏览器验证继续按钮、刷新与窄屏展示；相关后端冒烟和前端质量门通过后交付。

恢复入口需要数据库和已保存步骤可用；启动恢复失败会阻止服务接收新任务。流中的未落库 token 和进程内浏览器标签等临时资源不承诺原样恢复，续跑需要重新感知实际环境。
