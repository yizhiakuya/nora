## 1. 结论与审查口径

下一轮优化应优先消除重复状态、重复执行路径和重复参数处理。单服务收敛、SDK 工具绑定、前端死代码检查已经落地，应沿着现有设计继续收紧职责边界。

Nora 按单用户、单实例的个人 Agent 工作台评估。本轮重点检查聊天状态、工具执行、文件操作、HTTP 契约、依赖注入与质量门，没有逐文件完成全仓安全审计。

知识图谱工具在审查会话中不可用，使用源码、引用搜索、配置检查和现有检查命令核实。缓存竞态通过运行现有函数复现；其余问题主要依据源码链路分析，不等同于全部完成真实服务复现。

## 3. 优先修复的行为问题

### 1）合并普通路径与通配符路径的文件操作

**依据**：[AgentWorkspaceService.java](../../nora-api/src/main/java/com/nora/agent/service/AgentWorkspaceService.java)，`moveOrCopy`、`moveOrCopyGlob`、`copyDirRecursive`。

普通路径分支会拒绝把目录复制到自身子目录；通配符分支展开匹配项后直接调用复制，没有相同的源目标关系检查。

例如将 `photos/a*` 复制到 `photos/a/backup`，匹配到目录 `a` 后，实际复制目标落在源目录内部，会进入自包含递归复制路径。该结论来自源码分析，本轮没有执行该危险场景。

**最小方案**：通配符只负责展开源列表；普通路径和通配符统一生成源目标对，统一校验，再使用同一执行方法。目标映射、源目标包含关系、禁止覆盖及受保护路径检查在修改文件前完成。运行中的 I/O 失败仍需准确报告已完成项，不能把预检查描述为文件系统事务。

**改动范围**：工作区服务、`FileWorkspaceTools` 调用链、相关文件操作冒烟和真实文件验收。

**收益**：删除重复执行分支，避免两套路径规则继续分化。

**验收**：在临时目录中验证单文件、目录、通配符、目标冲突、复制到自身子目录和中途 I/O 失败；拒绝的操作不应先修改其他文件。

### 2）修正请求缓存的乱序覆盖

**依据**：[requestCache.ts](../../nora-web/src/lib/api/requestCache.ts)，`cached`；[agentApi.ts](../../nora-web/src/lib/api/agentApi.ts)，`fetchSessions`、`fetchSessionMessages`。

当前版本检查能阻止失效前的请求回填缓存，但强制刷新不会使旧请求失去回填资格。新旧请求并存时，最后完成的旧请求可以覆盖新结果。

本轮直接运行现有函数，按以下顺序复现：

1. 发起普通请求 A，暂不完成。
2. 对同一个 key 发起强制刷新 B。
3. B 返回 `new-result`。
4. A 随后返回 `old-result`。
5. 再次读取缓存，得到 `old-result`。

**最小方案**：同一 key 只有最新请求有权回填缓存。复用现有请求身份或版本机制，同时保留失效守卫和并发去重；旧请求仍可正常返回给原调用者，但不得覆盖新缓存。

**改动范围**：共享请求缓存及强制刷新调用方，重点关注会话列表、历史加载和标题轮询。

**收益**：在公共层解决乱序问题，减少业务层增加独立版本判断的需要。

**验收**：覆盖新请求先完成、旧请求先完成、请求中途失效、新请求失败，以及不同 key 互不影响。

### 3）技能保存成功后再关闭表单

**依据**：[SkillsView.tsx](../../nora-web/src/components/skills/SkillsView.tsx)，`handleSubmit`；[useSkills.ts](../../nora-web/src/hooks/useSkills.ts)，新增、修改、删除和启停方法。

表单调用保存后立即提示成功并关闭，但 store 方法返回 `void`，调用者不能等待真实结果。修改失败后通过重新拉取恢复；若网络持续不可用，拉取异常被静默忽略，界面可能保留未保存的数据。

**最小方案**：写操作返回 Promise，保存成功后以服务端结果更新列表，再关闭表单和显示成功提示。失败保留输入，并由明确的一层展示错误。技能管理属于低频写操作，可以删除临时 ID、部分乐观更新和回滚分支。

**改动范围**：技能 store、表单提交契约、列表与详情弹窗，以及聊天输入区和设置页中的启停入口。

**收益**：同时修正成功反馈、失败恢复和重复提交问题，减少状态补偿代码。

**验收**：真实服务下验证保存成功、参数拒绝、网络失败和重复点击；失败时没有成功提示，输入保留，重载后状态与服务端一致。

## 4. 收敛维护成本

### 4）让聊天消息只有一个前端状态所有者

**依据**：[useChat.ts](../../nora-web/src/hooks/useChat.ts)、[useChatSessions.ts](../../nora-web/src/hooks/useChatSessions.ts)、[agentApi.ts](../../nora-web/src/lib/api/agentApi.ts)。

同一会话的消息存在于 Hook 本地状态、会话 store 和请求缓存中。为协调这些副本，代码维护了定时回写、回声识别、历史收编、本地写入版本及恢复守卫。修改历史加载或终态处理时，需要同时理解这些同步规则。

**建议边界**：

- 现有会话 store 按 sessionId 管理消息；会话元数据与高频消息更新使用明确的订阅范围。
- Hook 负责输入、界面交互和连接生命周期，避免再保留一份可独立修改的完整消息。
- 复用已有事件 reducer 和 50ms 文本缓冲，发送与恢复继续使用同一事件处理链。
- 历史请求只做并发去重，避免额外保留一份完整历史缓存。
- 本地持久化继续只保存草稿及必要元数据，后端仍为完整历史的持久化来源。

**收益**：删除状态副本之间的同步协议。这是本轮维护收益最高的结构性优化，仅移动代码或拆分 Hook 文件不能实现这一收益。

**验收重点**：发送中切页与返回、迟到历史、断线重连、取消终态、排队插入与撤回、草稿保存，以及长输出期间的渲染次数。不能因统一 store 导致侧栏随每个文本增量重渲染。

### 5）普通聊天 HTTP 请求复用统一客户端

**依据**：[agentApi.ts](../../nora-web/src/lib/api/agentApi.ts)、[client.ts](../../nora-web/src/lib/api/client.ts)。

会话列表、历史、删除、截断和 live-turn 探测仍有手写 fetch、鉴权头、超时和错误处理。统一客户端已经具备信封解析、401 处理、服务端原始错误和链路 ID。

例如删除会话返回 409 时，手写路径只抛出 `deleteSession failed: 409`，没有保留服务端具体原因。

**最小方案**：普通 JSON 请求复用 `requestJson`，保留必要的数据映射；live-turn 等实时读取明确禁用缓存；有强制刷新需求的调用遵循统一缓存语义。SSE 继续使用专用传输，不强行套用 JSON 请求方法。

**改动范围**：聊天 API、统一客户端已有能力和相应调用方；迁移时逐项核对响应结构及缓存策略。

**收益**：直接减少重复代码，统一登录失效、错误正文和缓存失效行为。

**验收**：401、409、服务端结构化错误、网络失败、历史读取、删除与截断，以及正在运行轮次的实时探测。

### 6）工具参数进入类型系统后保持类型化

**依据**：[AnnotatedTools.java](../../nora-api/src/main/java/com/nora/agent/service/AnnotatedTools.java)、[FileWorkspaceTools.java](../../nora-api/src/main/java/com/nora/agent/service/FileWorkspaceTools.java)、[McpManagementTools.java](../../nora-api/src/main/java/com/nora/agent/service/McpManagementTools.java)、[ToolStepEmitter.java](../../nora-api/src/main/java/com/nora/agent/service/ToolStepEmitter.java)。

工具入口已完成结构校验和 SDK 绑定，但部分执行方法收到 record 后又转回 JsonNode，再通过字符串字段读取。步骤发射器的参数投影、标题、指纹和审批明细也分别解释工具参数，增加字段时容易漏改。

**最小方案**：先让执行方法直接使用 record 字段，删除不必要的 record → JSON → 字段读取。再收敛重复的参数归一化与展示投影，让标题、审批展示和步骤展示复用同一份已解析信息。

权限判定仍由统一权限门负责；展示对象不能代替执行参数或安全校验。MCP 的远端动态 schema、未知字段校验、脱敏、取消传播和原始结果状态必须保留。

**收益**：减少参数解释位置，扩大编译器能够检查的范围。无需新增通用工具框架，也不能为降低行数删除业务条件校验。

**验收**：必填与未知字段、错误类型、默认值、动作归一化、审批目标与实际目标一致、凭据脱敏、取消及 unknown/truncated 结果保留。

### 7）统一生产类与测试的依赖装配方式

**依据**：[TerminalService.java](../../nora-api/src/main/java/com/nora/agent/service/TerminalService.java)、[McpServerService.java](../../nora-api/src/main/java/com/nora/agent/service/McpServerService.java)、[ChatStoreService.java](../../nora-api/src/main/java/com/nora/agent/service/ChatStoreService.java)。

部分服务同时使用构造器、字段或 setter 注入；测试专用便捷构造器省略依赖，生产代码再通过 null 分支适配。测试对象与生产对象因此具有不同能力，依赖是否真正可选也不清晰。

**最小方案**：必需依赖通过一个构造器提供，测试显式提供对应依赖；只有真正可选的产品能力保留可选语义。若统一注入暴露循环依赖，先修正职责边界，不用延迟注入掩盖。

**改动范围**：相关服务的创建方式、Spring 装配及所有手工构造测试入口。

**收益**：减少构造重载和空值分支，使依赖关系及测试覆盖范围更可信。

**验收**：真实应用启动、命令运行与恢复、环境变量注入、MCP 连接以及历史执行状态读取。

### 8）把已有真实验收整理成可重复的质量门

**依据**：[quality.yml](../../.github/workflows/quality.yml)、[e2e-standards.py](../../scripts/e2e-standards.py)、[e2e-live-turn-client.mjs](../../scripts/e2e-live-turn-client.mjs)。

CI 已运行基础真实 HTTP 验收，但聊天恢复、取消、排队和浏览器状态等关键场景主要在独立脚本中。流恢复客户端验收还依赖本地 `logs` 下事先生成的代码产物和外部提供的事件记录。

**最小方案**：沿用现有脚本，建立固定入口，自动准备临时数据、编译产物和清理流程。明确哪些验收不需要模型，哪些需要真实模型及凭据；后者可单独运行，但缺少条件时必须明确记录未执行。

继续遵循项目约定：单测作无断言冒烟，业务行为由真实 HTTP/浏览器 E2E 验证。本建议不改变该约定，也不引入伪造业务结果的替代验收。

**收益**：结构调整后有稳定的行为证据，减少依赖本机日志和人工操作顺序的验证过程。

**验收**：从干净检出和临时数据环境出发，可以按文档命令执行；失败能定位具体场景，诊断材料不包含凭据。

## 5. 低成本性能优化

### 9）目录统计合并为一次遍历

**依据**：[AgentWorkspaceService.java](../../nora-api/src/main/java/com/nora/agent/service/AgentWorkspaceService.java)，`listDir`、`countEntries`、`dirTotalBytes`。

列目录时，每个子目录分别递归计算文件数和总大小，同一目录树被扫描两遍。照片库或包含大量依赖的项目目录会放大这部分 I/O。

**最小方案**：一次遍历同时累计数量和大小，复用遍历取得的文件属性；达到上限或出现读取失败时，明确统计不完整，避免把部分结果显示为精确总量。

**收益**：减少目录遍历和重复辅助逻辑。具体耗时收益需测量，本轮没有给出性能倍数。

**验收**：普通目录、空目录、大目录、权限受限项、符号链接和统计上限；在同一目录树下比较遍历次数与耗时。

## 6. 实施顺序与完成标准

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| 0 | 整理关键真实验收入口，对应第 8 项 | 核心场景可重复执行，外部条件与未执行项明确 |
| 1 | 修复第 1–3 项；统一第 5 项普通 HTTP 请求 | 具体缺陷消除，错误反馈与服务端状态一致 |
| 2 | 单独收敛第 4 项聊天状态 | 删除重复消息所有权和同步分支，发送/恢复/取消/排队验收通过 |
| 3 | 逐项处理第 6、7 项 | 删除重复参数转换与测试专用生产分支，真实启动和工具链验收通过 |
| 4 | 合并第 9 项目录统计 | 保留统计语义，减少遍历，并记录测量结果 |

每项先确定完整调用链和最小方案，再修改。阶段可以拆成小提交；不要同时重写聊天状态、工具执行和文件生命周期。

涉及实现的交付执行相应质量门：前端类型检查、Lint、Knip、冒烟和构建；后端完整 `mvn verify`，构建前处理运行同一 jar 的进程。随后执行对应真实链路验收，不能用冒烟通过代替行为正确。

## 7. 如何衡量优化收益

- **代码量**：记录生产源码净变化，区分删除、移动和新增验证代码；不把移动文件、删除注释算作主要优化成果。
- **维护成本**：检查一个字段或业务规则变更需要修改多少位置，以及是否仍需协调多份可写状态。
- **代码质量**：记录上述具体缺陷是否消除，失败路径是否保留真实错误与用户输入。
- **性能**：比较长输出期间状态提交/渲染次数、重复请求数量和目录遍历耗时。
- **依赖**：本轮确认可直接删除的依赖为 0 个；Knip 通过不等于全仓不存在冗余，但没有依据就不删库。

本轮不承诺整仓缩减百分比。净删行数应在实施后测量；合理的职责拆分可能不减少行数，但应减少同步规则、重复解释及一次修改需要触碰的位置。

## 8. 未验证范围与风险

本轮审查未修改业务源码。未执行真实模型/浏览器 E2E、生产升级、完整后端打包或长期负载测试；手机相册 MCP 独立仓库未深入审查。

缓存竞态已通过现有函数运行复现；文件通配符风险及其他行为问题依据源码链路分析，未执行危险文件操作复现。聊天状态和工具参数收敛涉及核心执行链，实施时必须保留取消、恢复、审批、脱敏与终态持久化语义，并逐项验收。
