# 运行中工作过程恢复与流式性能

## 问题与证据

`sess-1791612790023` 在 14:21:42、14:21:52 重开时触发 `cursor=0` 的回放缺口，最早缓存序号分别为 66344、68534。旧恢复链路创建空 assistant，再回放最近 8000 条事件；缺口处理又清空已有过程。完整 assistant 只在结束时写入消息历史，因此用户必须等到结束才看到早期过程。任务结束后历史仍有 131 个步骤，数据没有永久丢失。

这轮运行约 830 秒，42 次模型请求、52 次工具调用。历史接口返回约 924KB，用时 31–55ms。执行慢和页面渲染慢应分开衡量，不能把恢复后的空白误认为 Agent 没有执行，也不能把整个耗时归因于数据库。

## 最小设计

- `ChatTurnRunner` 已持有有序步骤、正文与思考缓冲，直接从这些状态生成完整快照，不再重建第二套运行状态、不增加逐 token 数据库写入。
- `TurnStreamRegistry` 在同一轮次锁内获取快照与订阅游标。首次接入或游标过期时发送一条 `snapshot`；窗口内重连继续按游标发送增量。复用已有回放门闩保证快照后的实时事件不超车。
- 接续连接立即发送标准 SSE 注释提交响应头；有效游标后没有积压事件时，也无需等待下一条业务事件才建立连接，注释不会推进游标。
- 快照包含工具状态、全部已接收的思考和正文、插入要求边界、引用、上下文计量、仍待处理的审批和提问。前端一次替换恢复消息，之后使用同一个流事件合并器继续更新。
- 事件窗口使用队列，淘汰旧事件无需移动整个数组。浏览器按 50ms 合并相邻同类、同轮次文本增量；控制事件与终态先刷新文本，再立即应用，顺序不变。
- 未变化的步骤不重复渲染；展开过程时不扫描所有工具结果提取折叠态画廊。

## 范围与验证

涉及轮次编排、恢复 SSE、前端 API/恢复 hook、过程组件及对应冒烟/E2E。保持历史存储、工具执行、取消、消息插入和压缩机制不变。验证长轮次超过事件窗口后的重开、窗口内续传、快照后的增量与终态、等待用户状态恢复、步骤顺序和重复、页面渲染次数。真实模型测试负责验收整个链路；不以模拟页面代替真实服务。

### 本地验收结果

- Typecheck、Lint、139 项前端冒烟、174 项后端冒烟和生产构建通过。
- `scripts/e2e-live-turn.py` 使用真实模型先执行平台命令、生成 1000 行正文、暂停提问，随后由浏览器刷新并回答，再执行第二条命令正常结束。首次打开及过期游标均返回完整快照；工具、思考、正文、引用和提问令牌保留，正文与原流逐字一致，有效游标只续传增量，终态历史保留全部步骤。
- `scripts/e2e-live-turn-client.mjs` 回放上述真实记录，验证批处理前后内容、步骤顺序、提问和计量完全相同。14,405 条事件只产生 59 次状态更新（按 512 条一批分散到刷新周期）；这是回放更新次数对比，不代表真实网络时序下的 FPS 或耗时比例。
- 浏览器实测刷新后早期命令仍可展开；回答后任务继续，结果仅出现一次，已手动展开的工作过程和工具详情不会在结束时被自动收起。

这次修复运行中恢复和渲染开销。原业务会话的 42 次模型请求、52 次工具调用仍需要独立分析工具选择与执行效率，不能把页面变流畅当作 Agent 总耗时已解决。
