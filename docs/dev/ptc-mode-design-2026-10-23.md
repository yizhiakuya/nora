# Nora PTC 模式设计

2026-10-23 用户确认目标是「模型写代码，在代码内串联或并行调用工具、处理结果后再回给模型」。未取得 DSH 源码，不声称协议或实现完全一致。下方编号章节保留原始设计，当前实现以本节为准。

## 2026-10-24 实施收敛

- 已实现：首页/聊天模式选择，会话与 Run 的 V44 持久化、入队冻结、父子步骤、SDK 顶层工具、真实容器编排和原权限门。标准模式默认不变。
- 受控入口直接复用 `ToolStepEmitter.invokeTool`，不增加拟议的 ToolInvocationService/ToolCallContext。PtcProgramService 只管编排，PtcRuntime 只管隔离、协议和串并行屏障。
- `execute_program` 只有 `code` 参数；`load_tools({names:[]})` 列目录，具体名称返回真实 schema。子结果 `{callId,status,content,truncated,artifacts}` 无虚构 data。父结果 `{output,calls,error}` 的 calls 由 Java 生成并保留成果引用。
- 无显式输出返回空 output 数组；console 的四种输出进入同一限额。超限明确报错，不自动归档大输出。图片由原通道提供给模型，文件与变更复用子工具/文件中心；不把脚本任意输出路径变成可访问资源。
- 代码/输出各 64 KiB、最多 256 项输出、128 KiB 消息帧、64 子调用、4 路安全读取、256 MiB 内存、32 PID、1 CPU。CPU 时间是每进程 60 秒，含等待总时限 10 分钟，不实现拟议的单独有效执行时间计费。
- 固定 digest 镜像必须预拉取，模式接口检查 Docker/image。容器无网络/宿主挂载/socket/生产凭据，只读根和 16 MiB tmpfs。可信 Node PID 1 只计时和启动；仅保留 SETUID/SETGID，清空附加组，将模型代码降到 UID/GID 65534、有效 capabilities 为零，使它不能杀死监督者绕过时限。全部 no-new-privileges。
- 取消按本次随机容器名回收并核对；Java 崩溃后容器监督者最迟 10 分钟退出，不启动额外扫全局容器任务。重启沿用 recoverStaleRuns，将 pending 转 declined、无终态 running 转 unknown，保留父子关系，不重跑代码。
- UI 显示原父工具行及按 callIndex 排序的子行，展开显示脱敏程序参数和结果；不新增日志面板。
- V44 只新增列及约束。关闭功能/回退前结算在途 Run，保留迁移、文件和 finalization 日志；旧镜像读取新历史兼容性未验证，不直接退回任意旧镜像。

中间验收：Maven verify、真实 Docker 集成、隔离数据库下真实模型 PTC HTTP 套件通过。已核对文件字节、历史恢复、拒绝无写入、批准后的实际写入、排队模式冻结及取消后新程序成功。最终前端、重启、生产验证待完成后补充，当前不代表已部署。未做 token/性能对照，不承诺节省比例。

## 1. 解决什么问题

标准模式由模型逐步请求工具，再读工具结果决定下一步。查多个文件、循环分页、合并统计时，中间结果经常不需要模型理解，却占用模型往返和上下文。

PTC（Programmatic Tool Calling）让模型提交一段 JavaScript，代码调用 Nora 现有工具、处理返回值，显式输出必要结果。仍由同一 Agent 决策和回答，同一 Run 管理生命周期；不是第二个 Agent，也不是把终端脚本换一个名字。

第一版交付：会话模式开关、单次脚本执行、串行调用与受限并发、显式输出、原权限审批、子步骤审计、取消/超时/重启恢复。标准模式保留，默认不改变已有会话。

不做跨轮持久 REPL、任意 npm 安装、脚本调度平台、自动重试写操作、自动判断应切换哪种模式。脚本跨轮变量不保留，需要复用的数据通过文件中心保存。

## 2. 已核对的当前链路

本次图谱工具不可用，以下依据当前源码，未把缺少图谱覆盖当作无引用证明。

| 当前入口 | 已有职责 | PTC 接入要求 |
|---|---|---|
| `ChatTurnRunner` / `ChatOrchestrationService` | Run 与模型循环、步骤事件、审批和提问 | 沿用原入口，解析并冻结本轮模式 |
| `ChatToolsSpec.forMessages` | 按历史加载工具，MCP 当前全部列出 | 标准模式保持；PTC 只给模型编排入口与发现入口 |
| `AnnotatedTools` | 从注解生成声明、参数绑定、SDK 执行 | 工具目录与子调用仍用同一注册表，不手写第二份 schema |
| `ToolStepEmitter` | 参数范围限制、审批、循环检测、执行、步骤与模型回填 | 将受控执行与模型回填分开，供两种模式共用 |
| `ChatToolExecutor` | 内置/MCP 分派、脱敏、限量输出、unknown/partial/媒体等结果 | 不是独立权限入口，脚本不得直接调用 |
| `ChatRunService` / `TurnCancellation` | 会话占用、取消 | 脚本和子调用都隶属原 Run |
| `ChatStoreService` / `ChatContextAssembler` | 步骤存储、历史与工具消息恢复 | 子步骤保留审计，但不伪造成模型直接发起的 tool call |
| `TurnStreamRegistry` / `ChatRunFinalizer` | 重连与终态持久化 | 父子步骤统一回放，终态落库先于通知 |

特别注意：当前审批在 `ToolStepEmitter` 中，而非 `ChatToolExecutor.executeTool`。PTC 直接调用后者会绕过审批；不能为脚本另外复制一套权限逻辑。

## 3. 用户入口与模式所有权

- 聊天输入区提供「标准 / PTC」两项；旁注「用代码批量处理工具结果」。权限档位仍单独显示，切换 PTC 不改变权限。
- 会话模式由后端持久化，前端缓存。新会话缺省 `standard`，旧会话迁移同值。
- 本轮启动时冻结 `executionMode`，保存到 Run；执行过程中切换只影响下一轮。排队请求在入队时记录有效模式，避免稍后切换使已排队请求的语义变化。
- 自动任务第一版继续标准模式，不新增任务配置开关；若内部以 PTC 执行，仍必须传递真实 unattended 标志，不能伪装为交互请求。
- PTC 不可用时明确显示运行时不可用及原因，不静默降级或在用户不知情时换成终端执行。

## 4. 模型工具契约

PTC 模式暴露 `load_tools`、`execute_program` 和顶层 `ask_user`。`load_tools` 复用现有名称，扩展为可检索内置/MCP 的统一目录；返回 canonical name、说明和真实参数 schema。已加载集合只属于当前历史与 Run，不新增跨会话缓存。

`execute_program` 参数：`code: string`、`description: string`。模型不传 sessionId、runId、权限、工作区路径基准或资源上限；这些全部由可信执行上下文绑定。

脚本 API：

```javascript
const result = await tools.call("工具的 canonical name", { /* 原工具参数 */ });
// result: { callId, status, content, data?, truncated, artifacts }
// status: completed / failed / declined / unknown / partial / cancelled
output(result.content);
```

- 使用统一 `tools.call(name, args)`，避免给任意 MCP 名生成 JS 标识符，也不传输可执行工具实现。
- `content` 保留现有工具结果文本。`data` 只在实际工具有结构化结果时提供；没有就缺省，不从 TSV/自然语言猜造 JSON。首版即使只有文本也能执行，但不承诺所有工具都有结构化可编排结果。
- `output(value)` 输出可 JSON 序列化值；不支持函数、循环引用和 BigInt，返回明确序列化错误。日志单独限量，默认不注入模型。
- 业务失败以可检查结果返回，传输/协议/脚本错误抛异常；取消强制终止程序，不允许脚本 catch 后继续调用工具。
- 未显式输出时返回「程序结束，未输出内容」及系统生成的执行摘要，绝不将整个堆或全部中间结果自动回填。
- 图片与文件使用已归档资源引用；`output` 引用只能指向本 Run 可访问成果，服务端验证并复用现有媒体与查看器契约，不让脚本输出任意文件路径或凭据 URL。
- 禁止嵌套 `execute_program`。发现工具和提问放在模型顶层完成；脚本中调用 `load_tools` / `ask_user` 返回可操作拒绝，避免第一版实现嵌套提问状态机。

示意（变量 `requests` 代表模型在读取真实 schema 后写入脚本的具体查询，不是新的 API）：

```javascript
const results = await Promise.all(
  requests.map(({ name, args }) => tools.call(name, args))
);
output(results.map(r => ({
  callId: r.callId,
  status: r.status,
  truncated: r.truncated,
  content: r.content
})));
```

真实任务应进一步筛选需要的字段或聚合数据；不靠把全部结果重新打印一遍获得虚假的 token 节省。

## 5. 执行架构与隔离

```text
模型 execute_program
  → 原 Run 中的 PTC 父步骤
  → 独立短生命周期 JS 容器
      ↔ 有长度限制的 JSON 消息通道（工具名、参数、调用序号）
  → Java 受控工具调用入口
      → 规范化与参数校验 → 数据范围 → 权限/审批 → 执行 → 持久化
      → AnnotatedTools 或 MCP
  → 脱敏结果回给脚本
  → output + 系统执行摘要 → 原模型循环
```

推荐首版采用固定 Node.js 运行镜像的短生命周期容器，每次 `execute_program` 一个实例，归原 Java 进程管理；不增加常驻网关或第二个业务服务。通过容器标准输入输出桥接，Nora 不通过 HTTP 调用自己的 Controller。

隔离基线：非 root、只读根文件系统、无网络、无宿主目录/生产工作区挂载、无 Docker socket、无生产环境变量；独立限量临时目录、CPU/内存/PID/输出限制、drop capabilities、no-new-privileges。平台管理员的 Docker 权限留在后端，不传入脚本容器。Node 的上下文封装只用于 API 组织，不能被当成安全边界；官方明确 `node:vm` 不适合独自隔离不可信代码：[Node.js VM 文档](https://nodejs.org/api/vm.html#vm-executing-javascript)。

JSON 通道本身也不可信：Java 绑定所属 Run、校验消息大小、序号和类型；不接受脚本声明的权限、完成状态或其他 Run 标识。即使脚本伪造通道消息，也只能请求自身上下文已允许的工具。协议原始输出不进入普通日志。

需验证部署环境确实执行上述隔离参数；初始化失败则 PTC 不可用。容器不是对内核漏洞的绝对隔离；本设计限于 Nora 现有单用户信任边界，多租户前须重新评估隔离方案。

建议首版固定限额（实现后以验收结果调整，暂不增加设置页面）：脚本 64 KiB、最多 64 次子调用、最多 4 个在途调用、脚本有效执行时间 60 秒、含审批的总墙钟时间 10 分钟、容器内存 256 MiB、输出总量 64 KiB。单工具沿用自身更严的限制，审批沿用 120 秒。有效时间包含等待工具，审批等待单独计时；任一总限额到达停止新调用并进入取消结算。

输出超限返回 truncated 与文件中心可读引用；脚本代码、完整日志和大结果仅在需要归档时走既有工作区归档与文件中心流转，不新增孤立存储。

## 6. 唯一受控工具入口

从 `ToolStepEmitter` 提取 `ToolInvocationService`（拟定名）：接收可信 RunContext 和工具名/参数，返回带真实终态的 invocation result；内部保留范围约束、参数校验、循环检测、风险分类、审批、running 先落库、执行与终态持久化。标准与 PTC 均调用它。

`ToolStepEmitter` 保留标准模式 SDK 消息回填与展示适配；PTC 子结果交给脚本，不能同时追加进外层 `messages`。并发子调用不共享可写的模型消息列表。

父步骤只代表受限编排，不以一次「批准整个程序」替代子调用审批。ASK 每个实际工具调用仍询问；ASSIST/FULL/无人值守规则沿用现行语义，权限检查使用归一后的真实目标参数。代码本身不获得额外网络或文件权限。

并发规则复用并整理现有 `canRunInParallel` 策略：只让明确可并发的操作同时运行；写入、浏览器/会话状态操作、未知 MCP 保守串行。风险等级低不等于无副作用，不能仅凭 LOW 判断。待串行操作设为队列屏障：等待之前在途调用结束，后续请求不能越过它；同一 Run 同时最多一个审批票据，避免覆盖当前单票据 UI。

循环检测和总次数跨父子调用共享。脚本内出现 unknown 或取消时，宿主停止派发新的副作用调用；不能依赖脚本自觉不重试。已进入执行的其他请求逐一结算并保留各自状态。

## 7. 结果、历史和界面

PTC 父步骤显示「批量处理 · N 个工具」，展开可看脱敏代码、子调用、执行日志和显式输出。子步骤继续使用现有工具卡片与审批卡；显示完成/失败/拒绝/未知/部分成功，不用程序成功结束掩盖某个写入失败。

在 `ChatStepDto` 和前端对应类型增加可选 `parentStepId`、`callIndex`；父子步骤仍在原步骤流里按 id 更新，不另建一套任务事件。UI 以 parentStepId 分组、callIndex 稳定排序；子步骤先到时暂存，父步骤到达后合并。旧步骤缺少这些字段仍按原列表呈现。

系统生成的结果摘要独立于 `output`，包含每个子调用的 id、名称、终态、截断标记和成果引用。脚本即使捕获错误、没有打印失败结果，模型和用户仍能知道失败事实。父步骤只有所有子调用成功且程序成功才标 completed；混合结果为 partial，存在未知副作用为 unknown，全部拒绝可为 declined；取消另行保留已发生的副作用。

模型历史只还原真实的外层 `execute_program` request/result 配对，子调用是嵌套执行事实，不得生成没有对应 assistant request 的 SDK tool result。`ChatContextAssembler`、压缩预算和归档同时更新，避免刷新后把全部子结果重新灌进模型。

全量结果仍受现有脱敏与单工具输出上限约束；PTC 的收益先来自省掉模型中间往返，不通过取消结果限额换取收益。原工具返回 truncated/unknown/partial、图片或成果失败时必须保留，不能在桥接层压成默认成功字符串。

## 8. 取消、失败和恢复

- SSE 断开：不取消程序；重连回放同一个 Run 的父子步骤和审批状态。
- 用户停止：标记 Run 取消，关闭桥接入口、停止新调用、取消在途工具并结束脚本容器；子调用结果落库后才释放会话占用。
- 工具已发出但远端结果不明：标 unknown，并阻止自动重放；不能因杀掉容器就宣称外部操作没发生。
- Java 重启/容器崩溃：不恢复 JS 堆、不重新跑代码；用已持久化的调用记录恢复。未执行为 interrupted，已执行无终态的副作用为 unknown。利用现有终态恢复规则，禁止将整段程序从头重跑。
- 编排完成时仍有未 await 的工具 Promise：停止接收新请求，并等待/结算已发出的请求；返回「存在未等待调用」，不能先宣布成功后后台继续写数据。
- 持久化失败：保留 existing finalization 恢复路径，失败不得触发重新执行；父步骤不可早于子步骤结算。
- 提问/补充要求：第一版提问走外层 `ask_user`；运行中新增输入进入现有队列，不注入执行中的 JS。用户要立即改变在途副作用时先停止，下一轮处理完整补充输入。

## 9. 实现改动与顺序

| 阶段 | 修改范围 | 完成标准 |
|---|---|---|
| 1. 统一执行入口 | `ToolStepEmitter`、新 `ToolInvocationService`、`ToolCallContext`、现有调用点 | 标准模式行为不变，审批/范围/取消真实回归通过 |
| 2. 编排内核 | 新 PTC 服务与固定运行镜像、桥接协议、`AnnotatedTools`、`ChatToolsSpec` | 单次代码、发现契约、串并行与资源终止通过 |
| 3. 会话与历史 | `ChatRequest`、会话/Run 存储、队列、上下文装配与压缩、终态恢复 | 模式快照准确、历史 SDK 消息合法、不重放副作用 |
| 4. UI 与发布 | `ChatInputArea`、`useChat`/会话 store、`lib/api/agentApi.ts`、步骤类型/卡片/流 reducer、部署配置 | 模式切换和父子步骤可见，断线与失败路径可验收 |

按职责拆分但作为一项完整能力交付，不发布只能执行代码却绕过审批或缺少恢复的中间版本。具体测试、迁移文件与前端类型路径在实施前按实际调用图补齐。

数据变更使用新增 Flyway 迁移：会话 `execution_mode` 默认 standard，Run 与排队输入保存有效模式；步骤 JSON 新字段可选。不得修改旧迁移。关闭功能时停止接收新 PTC Run，等待/结算在途调用，保留历史与文件；旧程序是否能正确读新步骤必须验证后才能回退镜像，不能仅靠默认值宣称向后兼容。

部署增加固定 digest 的 PTC 运行镜像和启动探测；不更新数据库拓扑、不挂载业务数据。资源回收只针对确属本 Run 的容器，启动恢复时核对标签与运行记录，不清理不明容器。

## 10. 验收与效果衡量

开发检查：后端 `mvn verify`；前端 typecheck/lint/deadcode/test/build。单测沿用不写结果断言约定，实际结果由隔离真实 HTTP/E2E 校验。

必须覆盖：

1. 同一批真实读取任务分别走标准/PTC，验证输出内容一致，记录模型往返数、输入 token、工具次数和墙钟时间；不预先承诺节省百分比。
2. 依赖串行、独立并行、串行屏障、最大并发与调用次数；分页终止与重复调用熔断。
3. 三档权限、批准/拒绝/超时、无人值守；脚本伪造权限/Run 标识无效，越界路径和检索范围无法逃逸。
4. 脚本死循环、内存耗尽、输出洪泛、非法协议、容器不可用；均有明确终态，后端仍能服务其他请求。
5. 部分成功、unknown、程序 catch 失败、未 await、取消竞争；核对真实副作用次数，不能仅看 HTTP 200。
6. 浏览器断连重连、刷新、后端重启、终态落库失败；没有重复写入，父子步骤/审批恢复正确。

## 11. 当前结论与待验证项

推荐方案是「同一 Agent + 会话 PTC 模式 + 受限 JS 编排 + 唯一受控工具入口」，第一版每次脚本独立运行。核心先决条件是拆开执行权限与模型历史回填，而非先加一个执行 JavaScript 的工具。

本轮只完成设计和源码核对；没有运行 PTC 原型、没有新增依赖、没有数据库迁移或生产部署。隔离运行镜像、桥接性能、实际 token 收益以及旧版本读取新历史的兼容性，均需实施阶段验证。DSH 具体 UI、持久 REPL 与 SDK 协议没有逐项核实，本设计不对此作等价承诺。
