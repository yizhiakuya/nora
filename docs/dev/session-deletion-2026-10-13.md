# 会话删除链路修复

## 问题与方案

线上 `sess-1791738154614` 已被服务端软删除，浏览器仍保留其本地索引。两个 UI 入口各自管理删除计时器，并用“列表里是否还有此 ID”判断是否执行删除；列表同步和详情加载会重新插入该记录，导致跳过删除或在后端返回不存在后恢复幽灵记录。删除当前会话也没有更新 URL。

统一职责：store 管理待删除快照、截止时间、提交与撤销；待删除项对同步和详情加载不可见；待删除操作持久化，刷新后继续提交。共享删除 hook 管理 toast 和路由，两个入口复用。提交成功失效旧列表响应，删除失败恢复记录并展示真实错误。当前会话删除后切到剩余会话或首页，撤销当前会话时恢复对应地址。

聊天工作区的会话作用域优先使用 URL 指定的 ID，避免本地列表移除或选中变化触发页面重挂载、丢失 404 导航。非聊天页面继续使用当前选中会话。

后端 DELETE 幂等：未知或已软删除的会话均视为已删除，仍保留活跃 Run 的互斥检查。详情 GET 使用明确的 404；客户端据此清除失效索引，不将它作为草稿复活。不会批量删除截图中的其他会话。

验证覆盖：同步与删除交错、迟到详情、撤销、真实删除后再次删除、草稿删除、失败恢复、刷新后的待删除提交和 URL 切换。只使用临时验收会话，不修改用户会话。

## 批量删除与连续刷新压力回归

2026-10-13 追加建立 8 个独立测试会话 `stress-6c498ee1-1` 至 `-8`，其中 4 个包含真实模型消息、4 个为空会话。浏览器可见列表确认已载入。页面删除命令实际完成前三个会话，但控制通道延迟、超时，不能据此声称完成快速 UI 连点。

剩余 5 个会话使用当前前端 store 经正式 HTTPS 执行：1ms 内连续登记删除并重复点击同一 ID；退出整个 Node/JSDOM 运行进程，丢弃所有旧定时器。约 1.1s、2.1s、3.4s 后分别在独立新进程从落盘快照恢复并同步真实列表，再在截止时间后核验提交，并额外重启一次。全过程约 7.7s；五个会话最终均返回 404、无待删除残留、无列表复活。

这是独立进程持久化恢复测试，未将其标记为真实浏览器快速刷新测试。8 个测试会话均已软删除；创建前的服务端可见会话清单为空，测试后仍为空。删除操作仅针对上述测试 ID，没有修改产品逻辑或再次部署。

最终实际刷新生产页面，使用最新 DOM 与截图确认侧栏仅保留用户原有的本地「新对话」草稿，无测试会话、旧失效会话或错误提示。浏览器 AX 接口曾返回过期快照，DOM 与截图复核后排除。数据库只读确认原问题 ID `sess-1791738154614` 仍为软删除、7 条历史消息仍保留。截图保存在 `logs/session-delete-fix/stress-final.png`。
